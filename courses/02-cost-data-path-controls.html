Part 1 · covers pricing mechanics

The bill has four lines

5 min live

Quick's monthly bill is seats, plus a flat fee per AWS account, plus agent hours beyond each person's allowance, plus index storage beyond the pooled allowance. The first two are fixed by head count. The last two move with behaviour, and one of them is metered in a way that surprises people.

LiveAgent hours are wall-clock, not thinking time3 min▶

AWS meters agent hours per second while Quick is active on a task, and the pricing page says that includes time spent waiting for an external tool to respond. A Research report that waits on a slow system, or a Flow scheduled to run every morning for every analyst, consumes hours whether or not anyone reads the output. The included allowance is 8 hours a person a month on Professional and 18 on Enterprise; beyond that each hour is $3. The three speed modes burn hours at different rates, and AWS does not publish the rates.

Two consequences for Priya. First, schedule Flows deliberately: one shared morning report beats twenty personal copies. Second, the admin limit profile is a budget control, not a nicety; on Essentials and Professional, overage only applies once an admin has set one.

Self-studyOlder numbers you will still find online2 min▶

Guides written at launch quote 4 and 8 included agent hours and a separate $6 rate for Research hours. The AWS pricing page read for this session says 8 and 18 included and a flat $3 for every agent hour. Trust the AWS page, and expect it to change again.

Part 2 · covers where data is stored and processed

Stored here, processed elsewhere

6 min live

AWS makes two statements that sound alike and are not. Stored customer data in Quick does not leave its AWS Region. Prompts and answers, while being processed, can be: Quick uses cross-Region inference, the customer cannot switch it off, and no log records which Region did the work.

LiveThree kinds of Region, and which one you are in3 min▶

AWS's Quick Regions page sorts the Regions with agentic features into two routing types, and a third group has no agentic features at all.

RoutingRegionsWhat it means
GlobalSingapore, Mumbai, Sao PauloBedrock's own definition of global inference: processed in any commercial Region
Within a geographySydney, Tokyo, N. Virginia, Oregon, Frankfurt, Ireland, London, ParisKept inside a bloc (US, EU) or a country pair (Sydney and Melbourne, Tokyo and Osaka)
No agentic featuresHong Kong, Seoul, Jakarta, Ohio, Canada and othersQuick Sight BI runs in 26 Regions; chat, Research and Flows do not run here

Web search crosses Regions too: from Frankfurt it runs in Ireland. Flow schedules run only in N. Virginia, Oregon and Ireland.

Self-studyThe documents disagree with each other3 min▶

Quick's outbound-connections page says processing stays "within the geography". Its Regions table lists Singapore, Mumbai and Sao Paulo as Global, and Bedrock's page defines global inference as any commercial Region. Both are AWS pages and they cannot both be the whole story for Singapore. A buyer in one of those three Regions should get AWS's answer in the contract, not from either page. The page also notes that Bedrock controls you may already use, service control policies and inference-profile permissions, do not apply inside Quick.

Real world

"Data never leaves the Region" is two promises. A data-residency clause usually names storage. Regulators increasingly ask about processing too. An honest vendor answer separates them, the way AWS's own pages do. A brochure that says only the first one is not wrong; it is incomplete.

Part 3 · covers controls

Three piles: reaches chat, needs Enterprise, does not exist

4 min live

Take the controls Oakmere's risk team asked for and sort them. Some reach every chat answer. Some exist only on Enterprise. Some stop at a boundary the demo never crosses. Lake Formation is the sharpest example: it reaches one path into Quick and not the others.

LiveActions widen the blast radius2 min▶

AWS's own agentic security page names the risk: it appears when an assistant can both read outside content and take an action. Automations sign in at service level, not with the permissions of the person who built them, and run unattended. Web actions run immediately with no human review by default. MCP and HTTP connectors can be added with no authentication. Compass's answer was to allow read-only SQL and nothing else. Quick's answer is configuration: approval steps, authenticated connectors and deny-by-default, most of it on Enterprise.

Build-along

Talk to data, then read what it wrote

★ 22 min · everyone builds

Dataset Q&A turns a question into SQL and shows its working. The skill to build is reading that SQL as a reviewer would, because the answer is only as right as the query. Use a small public table: any CSV you can upload as a dataset works, and an Athena table works if your trial account can reach one.

Create a dataset from a small table. Upload a CSV of a few thousand rows with a date column, a category and an amount, or point at an Athena table. Name every column plainly. Note whether the dataset is queried directly or imported into SPICE: Part 3 showed why it matters.

★ Step 1 · your dataset cardSource: claims_sample.csv (public sample, 5,000 rows) Columns: claim_date, product, region, paid_amount Mode: SPICE import / direct query (circle one)

Ask a question with a hidden trap. "Last month" depends on today's date and on which date column counts. "Claims" might mean count or amount. Ask it the way a claims manager would, then open Explain.

★ Step 2 · the questionHow much did we pay on motor claims last month?

Review the SQL for four things. Write down what it chose for each. A reviewer is looking for silent choices, not syntax errors.

★ Step 3 · the reviewTable: right one? __ Filter: product = 'motor'? __ (or 'Motor'? 'MOTOR'?) Aggregation: SUM(paid_amount)? __ (or COUNT?) Time window: calendar last month? __ (or last 30 days?)

Fix the meaning, not the question. Add a field description to paid_amount ("amount paid to the claimant, in SGD") and a synonym ("claims cost" for paid_amount). Ask again with different wording. Did the SQL change for the better?

Turn on the evidence trail. As an admin, find the chat logging settings and switch on delivery to CloudWatch or S3. Ask one more question, then open the log. Write down what it records and what it does not: AWS says it excludes the retrieved text.

★ Step 5 · what the log holdsRecorded: __________________________ Not recorded: __________________________ Default state before you switched it on: off

Compare with Compass. Compass's text-to-SQL faces the same four traps. Quick's advantage is the Explain view and the curation tools; Compass's is that every query runs through Athena under the asker's identity, so Lake Formation applies. Neither gets accuracy for free.

Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · A Flow runs a Research report for each of 40 analysts every weekday, and each run waits two minutes on a slow internal system. What happens to agent hours?

AWS meters agent hours per second while active, including waiting on external tools, and says scheduled tasks consume hours on every run. One shared report would cost a fortieth as much.

2 · Oakmere runs Quick in Singapore. Which statement is accurate?

Storage and processing are separate promises. Singapore is listed with Global routing, and AWS says Bedrock controls such as service control policies do not apply inside Quick.

3 · Compass hides customer_id below clearance 3 with Lake Formation. Oakmere imports the claims table into SPICE and builds a chat agent on it. What holds?

Lake Formation per-user rules reach Quick only on direct Athena queries with Identity Center propagation. SPICE is not supported, and chat enforcement is not documented. Encryption at rest does not hide a column from a user.
